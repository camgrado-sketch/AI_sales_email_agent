# Bug Report: 交互、模板预览与图片提取问题分析

**报告日期**：2026-08-06
**测试分支**：`develop` (合并了 `feature/task-stage-a-f` 的版本)
**反馈来源**：人工黑盒测试

---

## 1. 问题分析与根因定位

### 1.1 交互界面不友好
**现象**：
- 状态栏、上个步骤、当前交互区缺乏视觉隔离，排版混乱。
- 预览报错抛出大段英文（Playwright 缺失），对非技术用户极不友好。
- "强制生效模板"概念晦涩，用户不理解。

**根因分析**：
- `cli_controller.py` 中 `print_status_bar()` 的分隔符不够明显，清屏（`clear`）机制缺失。
- `preview.py` 在 Playwright 启动失败时，直接将原始异常信息 `e` 打印到了终端。
- 提示文案（如 `是否将 'xxx' 设为强制生效模板（覆盖自动阶段规则）？`）是阶段 A 移除阶段逻辑前残留的旧文案，未随 PRD 彻底清理。

### 1.2 模板确认与语言版本预览缺陷
**现象**：
- 用户反馈"没有将中英文模板都跳出确认，需要先进入模板文件夹，再选择中英文模板单独确认"。
- 导入生成时抛出 `language 生成失败` 报错。

**根因分析**：
- `template_importer.py` 的 `build_preview_html` 仅读取了 `template.html`（通常是源语言版本），未去读取 `template_cn.html` 和 `template_en.html`。
- 因此，`open_template_preview` 只能打开一个窗口，无法让用户分别预览双语版本。
- `language` 生成失败可能与 LLM 结构化输出解析时，某些字段（如 `cn_html` 或 `en_html`）缺失或命名不符有关。

### 1.3 模板内容生成问题（图片提取失效）
**现象**：
- 测试的 docx 中的图片没有被自动提取到 assets 中，生成的邮件全是图片占位符。
- 素材占位符位置与数量不符合原模板。

**根因分析**：
- `template_importer.py` 的 `_docx_to_markdown` 提取图片时，使用的是 `doc.part.related_parts.get(embed)`，但在某些 Word 版本或特定插入方式下，`embed` ID 可能无法正确解析出图片二进制数据，导致提取失败。
- LLM 在重写 HTML 时，因为上下文窗口过长或 Prompt 约束不够，导致图片/文件占位符被错误移动或遗漏。

## 2. 修复任务规划 (TASK)

已同步更新至 `tasks/TASK.md` 的新阶段 G。

### 阶段 G：体验优化与图片提取加固

**G.1 终端 UI 与文案净化**
- **目标**：优化 CLI 交互体验。
- **验收标准**：
  1. 引入清屏机制，确保每次进入新菜单时界面清爽。
  2. 捕获 Playwright 报错，拦截大段英文栈，改为一句中文友好提示（如"本地无浏览器环境，已生成截图"）。
  3. 彻底删除"强制生效"、"覆盖自动阶段"等旧概念文案，统一改为"设为当前生效模板"。

**G.2 双语模板分离预览与确认**
- **目标**：确保中英文模板都能被预览。
- **验收标准**：
  1. 重构 `build_preview_html` 和 `_confirm_template_flow`，在确认环节依次打开 `template_cn.html` 和 `template_en.html`。
  2. 修复 `language` 字段解析异常的边缘情况，增加容错和日志。

**G.3 docx 图片提取机制加固**
- **目标**：解决部分 Word 文档图片无法提取的问题。
- **验收标准**：
  1. 优化 `_docx_to_markdown` 的图片提取逻辑，支持遍历文档所有 shape 和 inline 图片。
  2. 强化 LLM Prompt：明确要求"绝对禁止改变图片占位符和文件占位符的相对位置与数量"。

**G.4 可视化编辑器预研（架构评估）**
- **目标**：响应用户关于"网页/doc 界面直接修改模板"的新需求。
- **验收标准**：
  1. 仅做技术评估：在 `docs/architecture.md` 中新增章节，评估从纯 CLI 升级为本地 Web UI（如 FastAPI + 简单网页编辑器）的可行性，不写代码。
